# Пайплайн генерации и валидации mysteryStart

## Цель

Получать тайны для города-государства, которые:

- соответствуют канону и выданным якорям;
- реализуют выданный тип тайны;
- используют заданную топологию причинного графа;
- имеют полноценную причинно-следственную модель;
- не содержат временных противоречий, знаний и сущностей «из ниоткуда»;
- не добавляют в `X`, `synopsis` и `entry` эффектов, которых нет в истинной причинной модели;
- дают игроку расследуемую тайну, а не просто необъяснимую аномалию;
- не становятся абсурдными ради масштаба, драматичности или ассоциативного поля.

Приоритет — сохранить дешёвую генерацию на **GPT-5.6 Luna, reasoning none**, а качество контролировать каскадом из двух judge-моделей.

---

# 1. Архитектура

На одну тайну допускается максимум **3 полные попытки генерации**.

Каждая новая попытка строит историю заново из тех же системных вводных:

- canon;
- mystery type;
- `type.about`;
- association;
- graph template;
- mask;
- anchors;
- выданные имена;
- остальные числовые параметры истории.

Не передавать следующему генератору проваленную историю и замечания judge. Это именно **полная регенерация**, а не repair.

Пайплайн:

```text
ATTEMPT 1
    ↓
Luna generator
    ↓
Luna judge
    ├─ PASS      → ACCEPT
    ├─ FAIL      → ATTEMPT 2
    └─ UNCERTAIN → Terra judge
                       ├─ PASS → ACCEPT
                       └─ FAIL/UNCERTAIN → ATTEMPT 2

ATTEMPT 2
    ↓
тот же процесс
    ↓

ATTEMPT 3
    ↓
тот же процесс
    ↓
если не ACCEPT → GENERATION_FAILED
```

## Правила маршрутизации

### Luna judge возвращает `PASS`

История принимается без Terra.

### Luna judge возвращает `FAIL`

История сразу отклоняется. Terra не вызывается.

### Luna judge возвращает `UNCERTAIN`

История передаётся Terra judge.

### Terra judge возвращает `PASS`

История принимается.

### Terra judge возвращает `FAIL`

История отклоняется и полностью генерируется заново, если остались попытки.

### Terra judge возвращает `UNCERTAIN`

Считать это `FAIL`.

Мы предпочитаем выбросить потенциально хорошую историю, чем сохранить причинно сломанную.

---

# 2. Что передавать judge

Judge не должен генерировать новую историю и не должен исправлять существующую.

Передавать ему:

```yaml
type:
  name: ...
  about: ...

association:
  name: ...

anchors:
  ...

graphTemplate:
  ...

nodes:
  ...

edges:
  ...

newCharacters:
  ...

synopsis: ...
entry: ...
closeWhen: ...
asksSequel: ...
```

Также передавать необходимый канон.

Если инфраструктура позволяет выделить только релевантный канон — это предпочтительно. Но judge должен видеть достаточно фактов, чтобы проверить:

- существование и свойства использованных сущностей;
- допустимость магии;
- роли персонажей и институтов;
- соответствие якорям.

Judge не должен получать скрытые инструкции генератора вроде «будь креативным». Его задача исключительно валидационная.

---

# 3. Рекомендуемый формат ответа judge

Оба judge используют один формат.

```json
{
  "verdict": "PASS | FAIL | UNCERTAIN",
  "issues": [
    {
      "code": "BROKEN_CAUSAL_EDGE",
      "location": "C -> X",
      "reason": "C объясняет, почему люди ушли, но не объясняет, почему они отсутствуют сейчас."
    }
  ],
  "summary": "Короткое итоговое объяснение решения."
}
```

## Ограничения

- При `PASS` поле `issues` должно быть пустым.
- При `FAIL` должен быть хотя бы один конкретный issue.
- `UNCERTAIN` использовать только тогда, когда модель не может надёжно решить вопрос из предоставленного контекста или причинность действительно неоднозначна.
- Judge не предлагает новую версию узлов.
- Judge не придумывает отсутствующие факты, чтобы оправдать историю.
- Judge оценивает только то, что реально написано в графе и каноне.

Рекомендуемые `code`:

```text
CANON_CONFLICT
ANCHOR_MISUSE
WRONG_MYSTERY_TYPE
BROKEN_CAUSAL_EDGE
TEMPORAL_CONTRADICTION
UNEXPLAINED_KNOWLEDGE
UNEXPLAINED_ENTITY
UNEXPLAINED_ACTION
IMPLAUSIBLE_ACTION
UNSUPPORTED_PHYSICAL_EFFECT
UNSUPPORTED_MAGIC
UNSUPPORTED_MASS_BEHAVIOR
MYSTERY_INCOMPLETE
UNSUPPORTED_X
MASK_LEAK
SYNOPSIS_ENTRY_INVENTION
CLOSE_WHEN_INVENTION
REDUNDANT_STRUCTURE
OTHER
```

# 4. PROMPT: Luna generator

Использовать для `mysteryStart` на GPT-5.6 Luna с `reasoning_effort: none`.

```text
Ты создаёшь новую тайну для текстового god-sim о городе-государстве на летающем острове.

Игрок — бог-покровитель города. Он узнаёт о происходящем через верховного жреца
и постепенно восстанавливает, что произошло на самом деле.

Система передаст:
- канон мира и текущее состояние города;
- тип тайны: name и about;
- шаблон причинного графа;
- маску открытых и скрытых узлов;
- мягкое ассоциативное поле;
- иногда один или несколько якорей из канона;
- одно-два имени для новых персонажей.

ТВОЯ ЗАДАЧА:
построить одну компактную, правдоподобную и полностью причинную историю
по заданному графу.

Сначала определи, что реально произошло.
Только после готовой истинной истории формируй то, что видит игрок.

==================================================
1. ОСНОВНОЙ ПРИНЦИП
==================================================

Тайна состоит из трёх слоёв:

ИСТИНА
Реальные события и состояния мира.

СЛЕДЫ
Наблюдаемые последствия истины.

ЗНАНИЕ ИГРОКА
Только часть следов и открытых фактов, доступная в начале истории.

Не строй истинную причинную цепочку задним числом ради эффектной завязки.

==================================================
2. УЗЛЫ
==================================================

Каждый узел — одно конкретное событие или состояние мира.

Узел не должен быть атмосферой, намёком или красивой недосказанностью.

Если действует человек, из узла должно быть понятно:
- кто действует;
- что именно он делает;
- чего хочет;
- почему выбирает это действие;
- что ему известно;
- откуда он это знает.

Если впервые появляется новая сущность — предмет, вещество, текст, инструмент,
группа, институт или иной объект, — сразу объясни:
- что это;
- откуда оно появилось;
- почему участвует в событии.

Не вводи сущность только для того, чтобы следующий узел стал возможен.

A — настоящая исходная причина данной цепочки.
Не начинай A с необъяснённой находки, неизвестного вещества или загадочного объекта.

==================================================
3. РЁБРА И ПРИЧИННОСТЬ
==================================================

Если дано A → B, событие B должно происходить именно ИЗ-ЗА A.

Для каждого ребра должно существовать простое предметное объяснение:

"A привело к B потому, что ..."

Если это предложение нельзя закончить конкретно без добавления новой информации,
перестрой A или B.

Для каждого ребра также проверь:

"Если бы A не произошло, почему B не произошло бы
или стало бы существенно менее вероятным?"

Если ответ слабый — связь слабая.

Не считай объяснением:
- "после этого";
- "из-за влияния";
- "из-за тревоги";
- "это заставило";
- "люди начали";
без конкретного механизма.

==================================================
4. ДОПУСТИМЫЕ МЕХАНИЗМЫ
==================================================

ДЕЙСТВИЕ
A меняет цель, возможность или решение человека, поэтому он делает B.

ЗНАНИЕ
A сообщает человеку конкретный факт.
Понятно:
- откуда он его узнал;
- как его понял;
- почему это изменило его решение.

ФИЗИКА
A материально, биологически, ремесленно или технологически вызывает B.

СОЦИАЛЬНОЕ РАСПРОСТРАНЕНИЕ
Понятно:
- как информация или поведение передаётся;
- почему отдельные люди его принимают;
- почему участников становится много.

КАНОНИЧЕСКАЯ МАГИЯ
Допустима только если именно нужное свойство магии уже установлено каноном.

Текст, символ, обряд, запрет, имя или произнесённые слова
сами по себе не являются физической причиной,
если такая причинная сила прямо не существует в каноне.

==================================================
5. ВРЕМЯ ГРАФА
==================================================

Причина всегда существует раньше следствия.

После заполнения узлов мысленно расположи их во времени.

Для каждого A → B проверь:
- A уже произошло к началу B;
- B не требуется для того, чтобы A стало возможным;
- объяснение ребра действительно объясняет B, а не другой узел;
- граф не создаёт временного цикла.

Если временной порядок нарушен — перепиши содержание узлов,
сохранив заданную топологию.

==================================================
6. ШАБЛОН ГРАФА
==================================================

Если система дала шаблон графа — используй ровно эту топологию.

Не добавляй дополнительную причинную ветку только ради драматичности.

Каждый узел должен выполнять необходимую роль в этой цепочке.

Если узел, предмет или действие можно удалить,
не изменив причинную историю, — убери его.

==================================================
7. ГЛАВНЫЙ ФАКТ ТАЙНЫ
==================================================

До написания X сформулируй для себя одним предложением:

"Что именно требует объяснения?"

Полный скрытый граф обязан содержать достаточную причину именно этого факта.

Не путай событие, которое привело к проблеме,
с причиной самой проблемы.

Для пропажи людей
недостаточно объяснить, почему они куда-то ушли.
Нужно объяснить, почему они отсутствуют сейчас.

Для потери
недостаточно объяснить, почему вещь переместили.
Нужно объяснить, почему она сейчас недоступна.

Для отравления
недостаточно объяснить контакт с носителем.
Нужно объяснить наблюдаемый вред.

Для саботажа
недостаточно объяснить доступ к системе.
Нужно объяснить сознательное нарушение её работы.

Для артефакта
недостаточно просто ввести необычный предмет.
Его скрытое происхождение, назначение или свойство должно причинно объяснять X.

==================================================
8. X — СТАРТОВАЯ АНОМАЛИЯ
==================================================

X — наблюдаемое следствие полной причинной цепочки
и старт расследования для игрока.

X должен:
- естественно следовать из предыдущих узлов;
- быть конкретным;
- вызывать вопрос "почему это произошло?";
- давать повод расследовать.

X не является отдельной сценой, которую можно свободно украшать.

Каждый факт внутри X должен быть непосредственным следствием
конкретного узла графа.

Не добавляй в X:
- новый эффект;
- новую реакцию людей;
- новую сущность;
- дополнительную угрозу;
только ради драматичности.

X не обязан напрямую затрагивать весь город.

Предпочитай:

небольшой конкретный симптом
+ большие возможные последствия

вместо:

необъяснимой массовой аномалии.

==================================================
9. МАСШТАБ И STAKES
==================================================

Тайна должна быть значима для города,
но масштаб наблюдаемого события и масштаб последствий — разные вещи.

Значимость может идти от:
- угрозы важной городской системе;
- возможного дальнейшего развития;
- риска неправильной реакции властей;
- политического или религиозного конфликта;
- влияния на снабжение, безопасность, стабильность, веру или знания.

Не делай массовое одинаковое поведение,
если отдельно не объяснены:
- распространение;
- причина индивидуального участия;
- причина массового масштаба.

==================================================
10. ЕСТЕСТВЕННОСТЬ ДЕЙСТВИЙ
==================================================

Причинная связь может быть формально возможной, но неправдоподобной.

Для каждого важного человеческого действия спроси:

"Сделал бы разумный человек это,
если бы следующего узла сценария ещё не существовало?"

Действие должно быть разумно из ситуации самого персонажа,
а не потому, что автору нужно подготовить следующий узел.

Если поступок выглядит специально сконструированным ради будущего эффекта —
замени его более естественным.

==================================================
11. ТИП ТАЙНЫ
==================================================

Тип тайны обязателен.

Система передаёт:
- name — короткое название;
- about — точное описание структуры скрытой истины.

Следуй прежде всего about.

name не является списком жанровых декораций.

Если название типа вызывает очевидное клише,
а about допускает более широкую реализацию —
следуй about.

Ищи конкретное воплощение типа внутри устройства именно этого города.

==================================================
12. АССОЦИАТИВНОЕ ПОЛЕ
==================================================

Ассоциативное поле — очень слабый творческий импульс.

Оно:
- не является фактом мира;
- не является обязательной темой;
- не обязано быть узнаваемо игроком;
- не должно воплощаться буквально.

Оно может слегка повлиять максимум на один-два элемента:
- характер причинной связи;
- форму наблюдаемого следа;
- отношение между уже существующими элементами;
- характер X.

Не создавай ради него:
- новую сущность;
- дополнительное событие;
- отдельную сюжетную линию;
- символическую практику.

Если хорошая причинная история лишь слабо резонирует с полем —
это допустимо.

==================================================
13. ЯКОРЯ
==================================================

Если система дала якорь, он должен реально участвовать в причинной модели.

Якорь не обязан быть:
- причиной;
- предметом тайны;
- злодеем;
- разгадкой;
- центральной темой.

Он может быть:
- местом;
- системой;
- каналом;
- участником;
- объектом воздействия;
- способом обнаружения события;
- причиной первоначальной ошибочной гипотезы.

Конкретику строй вокруг выданных якорей.

Остальной канон используй прежде всего для:
- проверки совместимости;
- конкретизации уже выбранной линии;
- получения естественных деталей.

Не переключайся на более громкую проблему из общего канона.

==================================================
14. СКРЫТОЕ И НАБЛЮДАЕМЫЕ СЛЕДЫ
==================================================

Скрытый узел означает:
игрок не знает самого события или правильной причинной связи.

Но скрытое событие может оставлять естественные наблюдаемые следы.

Для каждого скрытого узла подумай:

"Что после этого реально осталось бы в мире?"

Возможные следы:
- физическое последствие;
- изменение поведения;
- отсутствие ожидаемого;
- свидетельство;
- несоответствие;
- изменение обычного процесса;
- распределение людей или предметов;
- результат уже совершённого действия.

След должен существовать из-за скрытого события,
а не добавляться специально как "улика".

След не должен прямо пересказывать скрытый узел.

Тайна должна давать игроку хотя бы одну естественную ниточку для расследования,
а не только необъяснимый X.

==================================================
15. ПЕРСОНАЖИ
==================================================

Используй только имена, которые дала система.

Своих новых имён не придумывай.

Использованных новых персонажей добавь в newCharacters:
- роль;
- коротко кто это.

Если персонаж сознательно что-то делает:
у него должна быть понятная цель.

Не делай злой умысел вариантом по умолчанию.

Допустимы:
- ошибка;
- страх;
- привычка;
- неверное понимание;
- конфликт интересов;
- попытка сделать полезное;
если они причинно объясняют действие.

==================================================
16. SYNOPSIS И ENTRY
==================================================

synopsis — краткая стартовая ситуация так,
как её сейчас понимают в городе.

entry — конкретное сообщение верховного жреца игроку.

Пиши их только после готового truth graph.

Разрешено использовать:
- открытые узлы;
- X;
- естественные наблюдаемые следы скрытых узлов;
- текущие гипотезы жителей, если ясно, что это гипотезы.

Нельзя раскрывать:
- скрытый узел;
- скрытый мотив;
- правильную скрытую связь;
- разгадку другими словами.

synopsis и entry не должны добавлять новые факты,
которых нет в X, открытых узлах или естественных следах truth graph.

Не создавай атмосферу вместо информации.
Сообщай наблюдаемые факты.

==================================================
17. closeWhen
==================================================

closeWhen формулируй только после готового графа.

Тайна считается раскрытой,
когда игрок установил ключевые неизвестные части существующей причинной модели.

Требовать можно только то,
что уже существует в узлах или рёбрах.

closeWhen может требовать:
- установить причину X;
- установить механизм конкретного ребра;
- выяснить роль существующего персонажа;
- установить происхождение уже существующей сущности;
- установить настоящий смысл уже существующего действия.

Не вводи через closeWhen:
- новый предмет;
- новый текст;
- нового свидетеля;
- новое событие;
- новую причинную линию.

==================================================
18. asksSequel
==================================================

asksSequel: true только если разгадка этой тайны
непосредственно обнаруживает новую самостоятельную проблему или конфликт,
которые прежде не были известны.

# 5. PROMPT: Luna judge

Не оценивай историю по жанровому стереотипу `type.name`.
Главное — структурное определение из about.

Не возникли ли скрытые дополнительные причинные ветви,

- относится ли объяснение ребра именно к B.

Если хотя бы одно ключевое ребро не работает — FAIL.

Для каждого A → B:

- A происходит раньше B;
- B не требуется для возникновения A;
- нет временного цикла;
- знания и решения персонажей появляются до действий, которые на них основаны.

Для каждого важного знания персонажа:

- есть ли источник;
- мог ли персонаж реально получить это знание к этому моменту;
- не знает ли он факта только потому, что этот факт известен автору.

Для каждого важного предмета, вещества, текста, инструмента или группы:

- объяснено ли происхождение;

- не введена ли она исключительно для закрытия следующего узла.

Для каждого важного действия:

- понятна ли цель или причина персонажа;

Если граф объясняет только путь к проблеме, но не саму проблему — FAIL.

Не раскрывают ли synopsis или entry:

- скрытую причинную связь;
- разгадку другими словами?

- текст;
- свидетеля;

- мотив;
- причинный механизм?

FAIL только за структурный лишний элемент, усложняющий причинную модель без функции.

На уровне пайплайна UNCERTAIN будет считаться FAIL,

==================================================
1. ПРОВЕРЬ ГЛОБАЛЬНУЮ ПРИЧИННУЮ МОДЕЛЬ
==================================================

Не ограничивайся локальной правдоподобностью соседних узлов.

Сначала восстанови всю цепь происходящего в целом.

Проверь:

- объясняет ли полный граф наблюдаемое X;
- нет ли временных противоречий между удалёнными узлами;
- не зависит ли раннее событие от информации или результата позднего;
- не объясняет ли история только начало процесса вместо его конечного состояния;
- не существует ли скрытой необходимой причины, отсутствующей в графе.

Для каждого ребра A → B должно быть верно:

1. A существует до B.
2. A делает B существенно вероятнее.
3. В тексте существует конкретный механизм.
4. Для объяснения не требуется неназванный факт.
5. Объяснение ребра относится именно к B.

==================================================
2. ПРОВЕРЬ ЦЕНТРАЛЬНУЮ ТАЙНУ
==================================================

"Какой главный наблюдаемый факт должен объяснить игрок?"

После этого отдельно проверь:

"Содержится ли в скрытых узлах полная достаточная причина этого факта?"

Не принимай за разгадку объяснение соседнего события.

Например:
- причина ухода людей не обязательно объясняет их продолжающуюся пропажу;
- причина перемещения вещи не обязательно объясняет её недоступность;
- контакт с веществом не обязательно объясняет симптомы;
- доступ к системе не обязательно объясняет саботаж;
- существование необычного предмета не обязательно объясняет его влияние на X.

Если центральный mystery predicate не объяснён — FAIL.

==================================================
3. ПРОВЕРЬ ЧЕЛОВЕЧЕСКУЮ ЛОГИКУ
==================================================

Для каждого существенного поступка восстанови:

- цель;
- знания;
- источник знаний;
- выбранный способ;
- ожидаемый персонажем результат.

"Сделал бы разумный человек это действие,
если бы не существовало необходимости подготовить следующий узел сюжета?"

Если действие имеет смысл только как авторский механизм —
это существенная ошибка.

Не требуй оптимального поведения.
Люди могут ошибаться, бояться, заблуждаться и иметь конфликт интересов.
Но их действия должны быть естественны из их собственной ситуации.

==================================================
4. ПРОВЕРЬ ФИЗИЧЕСКИЕ И СОЦИАЛЬНЫЕ МЕХАНИЗМЫ
==================================================

Физический эффект требует реального механизма.

Массовое поведение требует:
- распространения;
- индивидуальной причины участия;
- объяснения масштаба.

Магия допустима только в пределах канонически установленных свойств.

Не позволяй тексту, символу, обряду, запрету или смыслу слов
самостоятельно создавать физический или поведенческий эффект,
если канон этого не устанавливает.

5. ПРОВЕРЬ ПРОИСХОЖДЕНИЕ
==================================================

Каждое существенное:
- знание;
- вещество;
- предмет;
- текст;
- инструмент;
- группа;
- способность;
должно иметь понятное происхождение или уже существовать в каноне.

Особенно ищи сущности, введённые только для того,
чтобы следующий узел стал возможен.

==================================================
6. ПРОВЕРЬ ТИП И ЯКОРЯ
==================================================

Скрытая истина должна соответствовать `type.about`.

`type.name` — только название.
Не требуй жанрового клише.

Якоря должны участвовать в реальной причинной модели,
а не быть декоративными упоминаниями.

==================================================
7. ПРОВЕРЬ X
==================================================

Рассматривай X как проекцию truth graph, а не самостоятельную сцену.

Для каждого утверждения внутри X найди источник в конкретном узле или его естественном следствии.

Если X добавляет существенный:
- эффект;
- поступок;
- реакцию;
- угрозу;
- сущность;
которых truth graph не породил — FAIL.

Отдельно проверь, не увеличен ли масштаб события искусственно ради urgency/gravity.

==================================================
8. ПРОВЕРЬ МАСКУ И ЭКСПОЗИЦИЮ
==================================================

synopsis и entry могут содержать только:
- открытые факты;
- X;
- естественные наблюдаемые следы скрытых событий;
- явно обозначенные текущие гипотезы жителей.

Они не могут:
- раскрывать скрытый узел;
- раскрывать скрытый мотив;

- добавлять новую фактическую сцену;
- подменять отсутствующую улику авторским намёком.

Одновременно у игрока должна быть хотя бы одна реальная наблюдаемая ниточка для расследования.

==================================================
9. ПРОВЕРЬ closeWhen И asksSequel
==================================================

closeWhen должен требовать только факты и связи,
уже существующие в truth graph.

Если closeWhen требует установить то,
чего в графе нет, — FAIL.

asksSequel:true допустим только если сама разгадка
реально обнаруживает уже заложенную новую проблему.
Не требуй сиквела ради драматичности.

Не ставь FAIL за обычную конкретизирующую деталь.

Но если существенная сущность, действие или подлиния

==================================================
VERDICT
==================================================

PASS:
вся история глобально состоятельна;
ключевые рёбра работают;
центральная тайна полностью объяснена;
X следует из truth;

нет существенного конфликта с каноном и type.about.

FAIL:
существует хотя бы один существенный дефект.

UNCERTAIN:
только если объективно не хватает данных для проверки.
Не используй его как мягкий вариант FAIL.

При FAIL:
- перечисли конкретные проблемы;
- укажи узел, ребро или поле;
- объясни дефект кратко;
- не предлагай исправление.

Не оценивай литературную красоту, оригинальность или личный вкус,
если они не создают логическую или игровую проблему.
```

# 7. Логика ретраев

Псевдокод:

```ts
const MAX_ATTEMPTS = 3;

for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
  const mystery = await generateWithLuna(originalInputs);

  const lunaVerdict = await judgeWithLuna(mystery, relevantCanon);

  if (lunaVerdict.verdict === "PASS") {
    return success(mystery);
  }

  if (lunaVerdict.verdict === "FAIL") {
    continue;
  }

  // Luna: UNCERTAIN
  const terraVerdict = await judgeWithTerra(mystery, relevantCanon);

  if (terraVerdict.verdict === "PASS") {
    return success(mystery);
  }

  // Terra FAIL or UNCERTAIN
  continue;
}

return generationFailed();
```

## Важное правило

При новой попытке не просить generator «исправить замечания».

Каждый retry — **полная новая генерация** из исходных параметров.

Это сохраняет систему простой и не создаёт истории, собранные из последовательных заплаток.

---

# 8. Что логировать

Для последующей настройки моделей полезно сохранять:

```yaml
attempt: 1

generator:
  model: gpt-5.6-luna
  result: ...

lunaJudge:
  verdict: FAIL
  issues:
    - code: MYSTERY_INCOMPLETE
      location: C -> X
      reason: ...

terraJudge: null
```

или:

```yaml
attempt: 2

lunaJudge:
  verdict: UNCERTAIN

terraJudge:
  verdict: PASS
```

А для полностью проваленной генерации:

```yaml
status: generation_failed
attempts: 3
```

Это позволит позже посчитать:

- долю историй, прошедших с первой попытки;
- частоту `FAIL` по каждому коду;
- долю эскалаций Luna → Terra;
- долю случаев, когда Terra принимает сомнительную для Luna историю;
- среднее число генераций на одну принятую тайну;
- реальную стоимость одной принятой тайны;
- какие типы/графы/ассоциации чаще ломаются.

Эти данные важнее субъективного впечатления от нескольких отдельных прогонов.

# 9. Принцип системы

Генератор отвечает:

> «Придумай одну возможную истину».

Judge отвечает:

> «Докажи, что эта уже написанная истина действительно работает».

Luna judge должен дешёво отсеивать явные дефекты.

Terra не является вторым обязательным проходом.
Она используется только как арбитр, когда Luna не может вынести уверенный verdict.

Если за три независимые полные генерации не удалось получить историю,
прошедшую каскад, событие считается не сгенерированным.
