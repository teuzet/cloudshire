# Cloudshire v2: принципы агентской разработки

Согласовано с Ником 2026-11-11. Документ про то, *как* мы пишем и проверяем v2,
а не про устройство игры. Концепт игры и план рефакторинга лежат отдельно.

## Цель

Разработка идёт удалённо и в основном руками Claude. Отсюда три требования:

1. Любую фичу и любого LLM-агента можно проверить, не поднимая бота, Telegram и базу.
2. Слабая связность модулей обеспечивается механически (линтер, CI, хуки), а не
   только дисциплиной исполнителя.
3. Claude может по инструкции сам проверить фичу или агента и отчитаться, а
   результат проверки остаётся в репо.

## Стек

- TypeScript (strict), Node 20+, ESM.
- Схемы и контракты: zod. Из схем выводятся типы и JSON Schema для tool-calling.
- Тесты: `node:test` или vitest (выбираем при старте v2, главное — один раннер).
- Правила импорта: dependency-cruiser.

## 1. Архитектура

### Слои и направление зависимостей

```
clients/   тонкие входы: Telegram-бот, mini-app, CLI
   ↓
flows/     сценарии: ход жреца, день, генезис, посев
   ↓
agents/    LLM-агенты: каждый в своей папке
   ↓
core/      чистая логика мира: модель, правила, фронты
```

`ports/` содержит интерфейсы внешнего мира (LLM, Storage, Clock, Random, Notifier).
`adapters/` содержит реализации портов (OpenAI, Anthropic, Mongo, in-memory, fake LLM).

Правила:

- Импорт только вниз по слоям. `core` не импортирует ничего из проекта, кроме `ports`
  с типами Clock/Random.
- Агенты не вызывают и не импортируют друг друга. Склеивают агентов только `flows`.
- Никто, кроме `adapters` и точки сборки (`clients/*/main.ts`), не импортирует SDK
  провайдеров, драйвер Mongo или Telegram-библиотеку.
- Зависимости передаются явно (аргументом или объектом `deps`). Никаких глобальных
  синглтонов конфигурации, `process.env` читается только в точке сборки.
- Время и рандом тоже порты. Так тесты детерминированы при фиксированных seed и clock.

Все эти правила записаны в `.dependency-cruiser.cjs` и проверяются в CI и в
pre-commit хуке. Нарушение роняет сборку.

### Устройство агента

```
agents/priest/
  prompt.md        системный промпт (шаблон с плейсхолдерами)
  schema.ts        Input и Output в zod — это и есть контракт агента
  run.ts           buildPrompt(input) + parse(output) + run(input, deps)
  fixtures/        входы для тестов и evals (YAML)
  cassettes/       записанные ответы модели для контрактных тестов
  evals/           рубрики и проверки для прогонов с настоящей моделью
  README.md        что делает агент, чего не делает, известные слабости
```

- Публичный интерфейс агента: `run(input: Input, deps: { llm }): Promise<Output>`.
  Всё остальное внутреннее.
- `buildPrompt` и `parse` — чистые функции, тестируются без LLM.
- Новый агент создаётся скриптом `npm run new:agent <name>`, который раскладывает
  этот шаблон. Руками папки не собираем.

### Размеры

Ориентир: файл до ~300 строк, функция до ~50. Если больше, это сигнал разрезать,
а не правило ради правила.

## 2. Инструкции для Claude-разработчиков

- Корневой `CLAUDE.md` короткий: карта слоёв, запреты, команды проверки,
  definition of done. Черновик: [CLAUDE.draft.md](CLAUDE.draft.md).
- В каждом слое свой небольшой `CLAUDE.md` с местными правилами
  (`core/`, `agents/`, `flows/`, `adapters/`).
- В README агента записываются его границы и известные слабости, чтобы следующий
  исполнитель не «чинил» то, что задумано.
- Хук перед коммитом: typecheck, lint (включая правила зависимостей), быстрые тесты.
  Claude не может сдать работу с красными проверками.
- Один PR — одна фича или один агент. Изменения в чужом модуле в том же PR
  допустимы, только если без них фича не работает, и это объясняется в описании.

### Definition of done для фичи

1. Typecheck и lint зелёные.
2. Есть unit-тесты на логику и контрактный тест, если затронут агент.
3. Если меняется поведение агента или flow, добавлен или обновлён сценарий/фикстура.
4. Обновлены README агента и CLAUDE.md слоя, если поменялись правила.

## 3. Тестирование

Четыре уровня. Ни один не требует запуска бота.

| Уровень | Что проверяет | LLM | Когда гоняется |
|---|---|---|---|
| Unit core | чистая логика мира | нет | каждый коммит, CI |
| Контракт агента | сборка промпта, парсинг, валидация схемы, ретраи | fake / кассеты | каждый коммит, CI |
| Сценарий flow | flow целиком: состояние мира + реплики игрока → новое состояние и сообщения | fake / кассеты | каждый коммит, CI |
| Eval агента / живой сценарий | качество ответов настоящей модели | настоящий | **только по запросу Ника** |

### Контрактные тесты агентов

- Фейковый LLM-адаптер отдаёт записанный ответ из `cassettes/`.
- Проверяем: промпт собран из нужных частей входа, ответ проходит схему, битый
  ответ корректно отбрасывается или ретраится, ошибки провайдера обрабатываются.
- Кассеты перезаписываются отдельной командой с настоящей моделью
  (`npm run cassettes:record <agent>`), и только по запросу.

### Сценарии flows

- Сценарий — YAML: начальное состояние мира, последовательность реплик/событий,
  ожидания (изменения состояния, отправленные сообщения, вызванные агенты).
- Прогон: `npm run scenario <name>` с in-memory хранилищем, fake LLM, фиксированными
  clock и seed. Результат — снапшот состояния и лог сообщений.
- Тот же сценарий с флагом `--live` идёт на настоящей модели и превращается в
  плейтест (только по запросу).

### Evals агентов (настоящая модель)

- `npm run eval <agent> [--fixtures ...]`.
- Два вида проверок:
  - детерминированные: ответ валиден, значения в допустимых рамках, нет запрещённых
    паттернов;
  - LLM-судья по рубрике из `evals/rubric.md` (например, «жрец не вышел из образа»,
    «бит двигает фронт»). Судья выдаёт оценку и объяснение.
- Результат сравнивается с последним прогоном того же агента из журнала проверок.

## 4. Автономные проверки силами Claude

Решение: **с настоящими моделями Claude работает только по запросу Ника**.
Никаких ночных или PR-триггерных прогонов. Уровни без LLM гоняются в CI всегда.

### Как это выглядит

1. Ник ставит задачу словами: «проверь, как жрец реагирует на грубость игрока»,
   «прогони генезис на трёх сидах».
2. Claude при необходимости дописывает фикстуры или сценарий, гоняет evals и
   сценарии, читает выводы.
3. Результат записывается в журнал проверок в репо (см. ниже) и коммитится.
4. Claude присылает Нику короткий отчёт со ссылкой на запись в журнале.
5. Если исправление очевидно (правка промпта, схемы), Claude открывает отдельный PR
   и повторяет ту же проверку на ветке с исправлением, сравнение кладёт в журнал.

Отдельный вид проверки — **агент-игрок**: Claude играет за игрока через CLI-раннер
flows (`npm run play --live`) и пишет отчёт как после плейтеста.

### Журнал проверок

Все проверки с настоящей моделью логируются прямо в репо:

```
checks/
  2026-11-12-priest-rudeness/
    task.md        формулировка задачи от Ника, что и как проверяли
    report.md      выводы: что работает, что нет, примеры, сравнение с прошлым
    results.json   сырые результаты: входы, ответы модели, оценки, модель, цена
  INDEX.md         список проверок: дата, агент/flow, итог одной строкой
```

- `report.md` пишется для человека: сначала итог, потом проблемы с примерами,
  потом сравнение с предыдущей проверкой того же модуля.
- `results.json` нужен, чтобы следующая проверка могла сравниться с этой.
- Ключи API живут только в секретах окружения, в журнал не попадают.

## Что делаем первым в ветке v2

1. Скелет: tsconfig, раннер тестов, dependency-cruiser, pre-commit хук, CI.
2. Порты и адаптеры: fake LLM, in-memory storage, фиксированные clock и random.
3. Корневой CLAUDE.md и CLAUDE.md слоёв.
4. Скрипт `new:agent` и первый агент по шаблону вместе с контрактным тестом.
5. Раннер сценариев и команда `eval`, журнал `checks/`.
