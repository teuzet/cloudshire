# Cloudshire

Текстовая мультиплеерная игра для Telegram на LLM-агентах. Игрок управляет доменом (городом-государством на летающем острове) не напрямую, а через диалог с персонажем-связным — обычно правителем, с которым игрок говорит от лица божества-покровителя.

Документ описывает целевой продукт для закрытого тестдрайва (10–20 человек, ~неделя) и план реализации по этапам.

Исходный черновик идей: `Cloudshire.txt`.

---

## 1. Полное описание проекта

### 1.1. Жанр и фантазия

- Жанр: асинхронный текстовый god-game / narrative sim.
- Язык игры: только русский.
- Мир: множество доменов игроков в одном сезоне/мире.
- Домен по умолчанию: город-государство на волшебном летающем острове; кроме города на острове ничего нет.
- Домены большую часть времени изолированы: почти все действия резолвятся внутри домена.

### 1.2. Роль игрока

- У игрока ровно один домен на сезон.
- Новая игра при уже существующем домене в текущем сезоне запрещена.
- Игрок не пишет команды боту. Весь UX — диалог с LLM-агентом.
- До старта игры: агент-онбординг помогает войти в сезон и создать домен.
- В игре: чат с одним персонажем-связным. Связной рассказывает о делах домена, принимает указания игрока и время от времени сам пишет «новости» (в т.ч. после тика).

### 1.3. Что такое агент

Агент — LLM с:

- системной инструкцией;
- набором разрешённых API/tool-вызовов (native function calling провайдера);
- реальными хэндлерами этих вызовов (хэндлером может быть и вызов другого агента);
- возможностью отвечать пользователю (человеку или другому агенту).

Модель задаётся **на каждого агента** через конфиг. Базовый провайдер — OpenAI; нужны врапперы, чтобы подключать разные модели/провайдеры без переписывания игровой логики.

### 1.4. Основные сущности

#### World (мир / сезон)

Единый контейнер всех доменов игроков.

- Общий лор мира (факты о мироздании).
- Глобальные запланированные ивенты (затмение, метеоритный дождь, нашествие и т.п.).
- Win/lose conditions сезона (текст + проверка агентом-оценщиком после хроники). На старте копируются во все новые домены; позже возможны per-domain условия.
- Глобальный ритм времени: тики по серверному времени (по умолчанию раз в 2 часа).

#### Domain (домен)

Центральный объект игры игрока.

| Поле | Смысл |
|------|--------|
| Название | Имя города/острова |
| Стартовое описание | Сгенерированный текст при создании |
| Статы | 6 абстрактных атрибутов 0–100 |
| Состояние (state) | Текущие процессы/события (бунт, голод, осада, фестиваль…) |
| Pending actions | Действия на текущий тик (единственное, куда пишут персонажи между тиками) |
| Персонажи | Список; в MVP — один связной |
| Лор | Список фактов (см. ниже); хроника — подмножество с тегом) |
| Владелец | Telegram user id |
| Win/lose | Скопированы с мира при создании |

**Статы (рабочий набор):**

1. Благосостояние  
2. Вера  
3. Культура  
4. Стабильность  
5. Знание  
6. Сила  

Альтернативы на обсуждение: «Сила» → «Мощь» (звучит более государственно); «Знание» → «Просвещение». Пока в конфиге фиксируем исходный список; переименование — правка YAML.

Статы слегка ограничивают сторителлинг. На текущем этапе их меняет Resolver по итогам тика.

#### Lore (лор)

Единая сущность фактов о домене (и отдельно — о мире).

Каждый факт:

- порядковый номер;
- текст в свободной форме;
- игровая дата, когда факт появился;
- теги (например `chronicle`, `geography`, `population`…).

Хроника — не отдельное хранилище, а факты с тегом `chronicle`. **Добавлять chronicle-факты может только Resolver.**

На первом этапе лор отдаётся агентам целиком собранным текстом (без векторного поиска).

Агент лора (когда появится явно) может отвечать на фактологические вопросы и при необходимости выводить новые факты из известных + state + хроники и пушить их в БД с текущей игровой датой.

#### Character (персонаж)

Принадлежит домену.

- Имя, описание, портрет (портрет можно отложить).
- История диалогов (по тикам / сессиям).
- Доступ на чтение: лор, state домена.
- Запись: только в `pending_actions` — объявить действие, уточнить, отозвать.
- Не пишет напрямую в хронику и не меняет статы.

В будущем в `pending_actions` смогут писать и другие системы (глобальные ивенты и т.д.).

#### Pending actions

Узел стейта домена: список намерений/действий на ближайший тик.

Между тиками время «застыло»: идут диалоги, действия копятся в pending. На тике Resolver читает pending + state + лор и порождает новую правду мира.

#### Resolver

Главный агент резольва тика. Единственный источник правды о новой хронике.

На входе: лор (в т.ч. хроника), state, pending actions, персонажи, статы.  
На выходе: новые chronicle-факты, обновлённый state, обновлённые статы, очистка/ротация pending.

Инструкция Resolver — самая важная; на дистанции возможен файнтюнинг.

#### Conflux (слияние доменов)

Время от времени два домена временно объединяются (стыковка островов, портал, встреча кораблей…).

- Создаётся временный объект conflux (домены, тип, длительность).
- На время слияния общий Resolver заменяет резолверы обоих доменов.
- Стыковка по внешним правилам (не агент); для начала — нормированная случайность.
- Открытые продуктовые вопросы (решать на этапе Conflux): плотность событий vs обычный тик; в чью хронику писать общие/односторонние события.

#### Win / Lose

После каждой новой хроники агент-оценщик проверяет условия.  
Мета-прогрессия (мана, форс-conflux, реролл хроники и т.п.) **не входит** в тестдрайв. Условия нужны для ощущения сезона и возможного «выиграл/проиграл», без магазина меты.

### 1.5. Генерация домена

Отдельный модуль (логика + агент):

1. Раскидать **300 очков** случайно по 6 статам (итог каждого стата в разумных границах 0–100; сумма = 300, значит среднее 50).
2. Выбрать по одному случайному тегу из каждой сконфигурированной группы (пример групп: климат/почва, магия/технологичность, … — полный список в конфиге).
3. Агент по статам, тегам и инструкции генерирует название, описание домена и персонажа-связного.
4. Создать домен, начальный лор, пустой/стартовый state, скопировать win/lose с мира.

### 1.6. Движение времени

- Между тиками: диалоги; запись только в pending actions; связной может писать игроку.
- Тик: глобально для всего мира по расписанию сервера (каждые 2 часа) + `force-tick` в CLI для локальных тестов.
- На тике для каждого домена (или conflux): Resolver → хроника/state/статы → оценщик win/lose → связной может проактивно прислать новости игроку.

Позже: отдельное «текстовое окружение» (уточняется отдельно).

### 1.7. Клиенты

1. **Telegram-бот** — основной клиент для друзей.  
2. **Локальный веб-фронт** — имитация Telegram-чата с тем же пайплайном; позже — чит-кнопки для анализа (просмотр state, лора, force-tick, промптов и т.д.).  
3. **CLI** — управление сервером (наполняется по мере нужды): как минимум запуск, статус, force-tick; далее — список доменов, сброс тестовых данных и т.п.

Админ-UI не нужен.

### 1.8. Хранение данных

- Прод/длинная дистанция: **MongoDB**.
- Локально: **YAML-файлы** (или дерево YAML на сущность).
- В конфиге — переключатель хранилища модуля одним параметром (`yaml` | `mongo`), без смены игрового кода.

### 1.9. Вне скоупа тестдрайва

- Мета-валюта, мета-магазин, мана и мета-действия.
- Векторный поиск по лору.
- Файнтюнинг моделей.
- Полноценная админка.
- Портреты персонажей (можно заглужить).

## 2. Архитектурные принципы

1. **Агенты — тонкая политика, код — жёсткие инварианты.**  
   LLM предлагает действия через tools; сервер валидирует и применяет. Персонаж физически не может писать в chronicle; Resolver — единственный, кому это разрешено на уровне хэндлеров.

2. **Один источник правды на тип записи.**  
   Хроника только от Resolver. Pending — от персонажей (и позже системных писателей). Статы после тика — от Resolver. World задаёт сезон и расписание.

3. **Доменная изоляция по умолчанию.**  
   Код и промпты не требуют внешних доменов, пока нет активного Conflux. Conflux — явная смена контекста резольва, а не «всех во всех промптах».

4. **Провайдер LLM за враппером.**  
   Игровые модули вызывают `agent.run({ messages, tools })`, а не SDK конкретного вендора. Модель и параметры — из конфига агента.

5. **Storage за интерфейсом.**  
   `DomainRepository`, `WorldRepository`, … с реализациями Yaml / Mongo. Переключение в конфиге.

6. **Клиенты тонкие.**  
   Telegram и веб-фронт шлют «сообщение от userId» в один application-слой. Нет дублирования игровой логики в адаптерах.

7. **Конфиг важнее хардкода.**  
   Статы, группы тегов, интервал тика, win/lose тексты, model id агентов, system prompts — в YAML/конфиге.

8. **Plain JS, Node.js.**  
   Без TypeScript на старте. Простые модули, явные границы (`agents/`, `game/`, `storage/`, `clients/`, `cli/`).

9. **Сначала вертикальный срез, потом ширина.**  
   Каждый этап даёт наблюдаемое поведение (чат / тик / новости), а не только абстрактные слои.

10. **Проактивность связного — часть игры.**  
    После тика (и при необходимости в других точках) сервер сам инициирует сообщение персонажа игроку, а не ждёт входящего апдейта.

## 3. План реализации по этапам

На каждом этапе есть **критерий «можно смотреть»**: что запустить и что должно работать.

### Этап 0 — Каркас репозитория

**Сделать:**

- Структура папок, `package.json`, скрипты `start` / `cli`.
- Загрузка конфига (`config/default.yaml` и т.п.).
- Логирование, env для ключей API.
- Заготовка интерфейса storage + заглушка in-memory или yaml.

**Проверка:** `node` / npm-скрипт поднимается, конфиг печатается, CLI отвечает `help` или `status`.

---

### Этап 1 — Storage + модели данных домена

**Сделать:**

- Сущности: World (минимальный), Domain, LoreFact, Character, pending actions, state.
- Yaml-хранилище: CRUD домена, лора, привязка `telegramUserId → domainId`.
- Переключатель в конфиге `storage.driver: yaml` (mongo — заглушка или отложенная реализация).
- Сид одного тестового мира/сезона в конфиге или фикстуре.

**Проверка:** CLI создаёт/читает домен из YAML на диске; после рестарта данные на месте.

---

### Этап 2 — LLM wrapper + первый агент

**Сделать:**

- Wrapper OpenAI (native tool calls).
- Регистрация агентов из конфига: `model`, `instructions`, `tools`.
- Тестовый агент «эхо/помощник» с 1–2 tools (например `get_time`, `ping_storage`).

**Проверка:** CLI-команда `agent-ping` (или чат в REPL) вызывает модель, отрабатывает tool, возвращает ответ на русском.

---

### Этап 3 — Онбординг + генерация домена

**Сделать:**

- Модуль генерации: раздача 300 очков по 6 статам; выбор тегов из групп конфига.
- Агент генерации домена/связного.
- Агент онбординга: если у userId нет домена в сезоне — предложить создать; вызвать генерацию; запретить вторую игру.
- Старт: начальные факты лора (не chronicle или минимальный prologue — по согласованию в промпте).

**Проверка:** С локального фронта или CLI: новый user → диалог → домен создан в YAML со статами, тегами, описанием и персонажем. Повторный заход того же user не создаёт второй домен.

---

### Этап 4 — Чат со связным + pending actions

**Сделать:**

- Character-агент: читает лор/state (tools), пишет только в pending (declare / update / revoke).
- История диалога сохраняется.
- Маршрутизация: нет домена → онбординг; есть → связной.

**Проверка:** В веб-имитации чата поручение «подготовь запасы к зиме» появляется в `pending_actions`. Попытки «напрямую» попасть в хронику через tools невозможны (tool отсутствует / хэндлер отвергает).

---

### Этап 5 — Telegram-адаптер

**Сделать:**

- Long polling или webhook (для локалки — polling).
- Тот же application-слой, что у веба.
- Доставка исходящих сообщений userId → Telegram chat.

**Проверка:** С телефона/клиента Telegram тот же сценарий, что на этапе 4.

---

### Этап 6 — World tick + Resolver

**Сделать:**

- Scheduler каждые 2 часа + CLI `force-tick`.
- Resolver-агент: tools на чтение домена; запись chronicle-фактов, обновление state/статов, очистку pending.
- После тика — проактивное сообщение связного игроку (новости).

**Проверка:** Накидать pending → `force-tick` → в лоре новые факты с тегом `chronicle`, state/статы изменились, pending очищен/обновлён, в чат пришло сообщение от связного без входящего сообщения игрока.

---

### Этап 7 — Win/Lose оценщик

**Сделать:**

- Условия в конфиге мира.
- Копирование на домен при создании.
- Агент-оценщик после хроники; статус домена (playing / won / lost).
- Поведение чата при terminal-статусе (связной сообщает итог; онбординг новой игры в том же сезоне по-прежнему запрещён).

**Проверка:** Подставить тестовое условие и форс-тик/фикстуру хроники → домен переходит в won/lost, игрок получает сообщение.

---

### Этап 8 — Mongo driver

**Сделать:**

- Реализация тех же репозиториев на MongoDB.
- Переключение `storage.driver: mongo` без изменения агентов.
- Миграция/совместимость полей минимальная.

**Проверка:** Тот же сценарий этапов 3–6 на Mongo локально или в docker.

---

### Этап 9 — Conflux (первый вертикальный срез)

**Сделать:**

- Правила стыковки (случайность + конфиг).
- Объект conflux, общий Resolver на время слияния.
- Запись хроник в затронутые домены по простым правилам (зафиксировать выбор в коде/конфиге).

**Проверка:** Два тестовых домена → форс-conflux → force-tick → события касаются обоих; после окончания слияния снова отдельные резолвы.

---

### Этап 10 — World lore и глобальные ивенты

**Сделать:**

- Лор мира; tools у Resolver/персонажей на чтение world-lore по необходимости.
- Шедулер глобальных ивентов → запись в pending (или отдельный пайплайн) доменов.

**Проверка:** Наступает тестовый ивент → у доменов появляется pending/след в хронике после тика.

---

### Этап 11 — Полировка под тестдрайв

**Сделать:**

- Устойчивость к ошибкам LLM (ретраи, понятный fallback-текст игроку).
- Лимиты длины истории диалога / компакция.
- Чит-кнопки на локальном фронте (state, lore, pending, force-tick).
- CLI: status, list domains, force-tick, maybe inspect domain.
- Прогон на 2–3 друзьях, потом 10–20.

**Проверка:** Недельный сценарий: тики сами идут, игроки только переписываются со связным, данные не теряются, стоимость API приемлема.

## 4. Карта агентов (целевая)

| Агент | Когда | Главные tools |
|-------|--------|----------------|
| Onboarding | Нет домена | `create_domain` / start generation |
| DomainGenesis | Создание игры | (внутренняя генерация; может быть без user-facing chat) |
| Liaison (Character) | Игра | read lore/state; pending declare/update/revoke |
| Resolver | Тик | read all; write chronicle; update state/stats; clear pending |
| WinLoseJudge | После хроники | read domain+conditions; set status |
| ConfluxResolver | Тик в слиянии | как Resolver, на 2 домена |
| Lore (опционально позже) | По запросу | query/add non-chronicle facts |

## 6. Открытые решения (не блокируют этап 0–4)

- Точный список групп тегов генезиса (кроме примеров).
- Нужен ли отдельный Lore-агент или чтение лора — просто tool, отдающий склеенный текст.
- Политика длины промпта, когда фактов станет много (пока «всё в контекст»).
- Плотность событий и маршрутизация хроник в Conflux.
- Формат игровой даты (земной календарь / условные «тиковые эпохи»).

## 7. Порядок работ «с завтра»

Рекомендуемая последовательность поставки для просмотра:

**0 → 1 → 2 → 3 → 4 → 6 → 5 → 7 → 8 → 9 → 10 → 11**

Telegram (этап 5) можно поднять сразу после чата (4) или сразу после Resolver (6), если удобнее сначала отладить тики на вебе. В таблице выше этап 5 стоит перед 6 для раннего доступа с телефона; для локальной разработки часто выгоднее **4 → 6 → 5**.
